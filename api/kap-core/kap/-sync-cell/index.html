SyncCell

class SyncCell<A>

A typed, non-suspending thread-safe cell: the Ref semantics without the coroutine machinery, for the SPIs that cannot suspend.

A Ref operation is a Kap that takes a Mutex, so every read and write is a suspension point. That is the right default for graph code, and the wrong one for a callback: KapTracer.onEvent, a listener, a shutdown hook or an SDK's onClose are plain functions and cannot wait for a lock. SyncCell is the same piece of state with the same laws, implemented as a lock-free atomic register (AtomicReference + compare-and-set), so it can be read and written from any thread, from inside any coroutine, and from code that has no coroutine at all.

class Metrics : KapTracer {
    private val events = Ref.sync(0)          // no suspend, no Kap
    override fun onEvent(event: TraceEvent) {
        val seen = events.getAndUpdate { it + 1 }   // atomic, returns the previous count
        if (seen == 0) log.firstEvent(event)
    }
}

Laws

  1. Atomicity. Every operation is one atomic step: concurrent updates never lose a write (N threads incrementing M times leave exactly N * M), and every read observes a value the cell actually held (linearizable register).

  2. Read-modify-write. update, getAndUpdate and modify transform the value they observed: the transform is retried until it lands on a value that is still current, so a concurrent writer forces a recomputation, never a lost update.

  3. No suspension. No operation suspends, allocates a coroutine, or takes a lock: it is safe inside KapTracer.onEvent, a signal handler or a plain Thread. (On single-threaded targets — JS, Wasm — the atomics are trivially atomic; the contract is identical.)

  4. Same value semantics as Ref. get/set read and replace; update returns the new value; getAndUpdate returns the previous one; modify stores the first component of the pair and yields the second.

Contract on the transform

The transform passed to update, getAndUpdate and modify must be pure and fast: under contention it is called again with the newly observed value (the compare-and-set failed because someone else wrote first), so it must not depend on side effects or on being called exactly once, and it must not call back into the same cell.

Type Parameters

A

the type of the state. Immutable values are the honest choice: the cell stores and returns references, so mutating a returned object is outside the atomicity guarantee.
