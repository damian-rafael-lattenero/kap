KapProcess

class KapProcess<A>(val name: String, val backpressure: Backpressure = Backpressure.Suspend, val itemBudget: Duration = Duration.INFINITE, observe: (MailboxEvent<A>) -> Unit = {})

A typed mailbox process — "actors yes, Akka no" (SPEC-5.0): a bounded queue of a user ADT A, a named backpressure policy (Backpressure, the same algebra KapStream uses), a single-consumer drain with per-item failure isolation and a per-item time budget, and a lifecycle that is a Process (kap-resilience) with all of its laws: normal completion, stop and scope cancellation are never failures, a failure restarts under the policy, and the heartbeat beats while the drain runs.

sealed interface Command
data class EnforceMode(val taskId: String) : Command
data class RefreshMenu(val taskId: String, val options: List<Option>) : Command

val mailbox = KapProcess<Command>(
    name = "stream-effects",
    backpressure = Backpressure.Buffer(256),   // exact: the producer waits, nothing is lost
    itemBudget = 45.seconds,                    // one stuck effect can never stall the loop
    observe = { event -> log(event) },          // drops, failures and timeouts as data
)

coroutineScope {
    val worker = mailbox.asProcess(handler = { command -> runEffect(command) }).startIn(this)
    mailbox.offer(EnforceMode(taskId))          // from the pump: suspends only if the buffer is full
    awaitShutdownSignal()
    worker.stop()                               // idempotent, not a failure
}

Module placement

KapProcess lives in kap-stream on purpose. The minimal-code law asks for the smallest home that already owns the required pieces: kap-stream owns Backpressure (the mailbox's policy value) and already depends on kap-resilience (the Process lifecycle). A dedicated kap-actors module would add a Gradle module, a publication coordinate and a new dependency edge for ~250 lines that reuse exactly these two algebras. The mailbox is the same backpressure algebra with one consumer instead of a stream of stages; it belongs next to it.

Laws

  1. Exact strategies never drop. Backpressure.Suspend and Backpressure.Buffer hand every offered item to the handler, in offer order, and dropped stays 0. The producer suspends exactly where the strategy says (always for Suspend, only when full for Buffer).

  2. Lossy strategies drop only what they say — and count it. Conflate, Latest(n) and DropOldest(n) keep the newest n (Conflate = one), DropLatest(n) keeps the oldest n and drops the incoming element. Survivors keep offer order and are never duplicated, and every lost item increments dropped exactly once (offers after close included). delivered + dropped == offered once a closed mailbox has drained.

  3. At most one handler at a time. The drain is a single sequential loop; starting a second consume on the same mailbox is rejected, so two handlers can never overlap.

  4. Failure isolation. A handler throwing an Exception is reported as MailboxEvent.Failed and the drain continues with the next item; the surrounding Process does not restart. CancellationException is never an item failure: it propagates (cancellation is sacred).

  5. Budget, not abandonment by silence. An item whose handler exceeds itemBudget is cancelled and reported as MailboxEvent.TimedOut; the next item starts immediately. The handler's finally blocks still run.

  6. Process lifecycle. Normal completion is close followed by a drained mailbox; stop() and scope cancellation are never failures; a fatal failure of the drain (an Error, or an error in the observer) restarts it under the RestartPolicy. The heartbeat beats while the drain runs, independent of handler progress.

The mailbox as a supervised Process — the SPEC-5.0 actor with the Process laws. The body is consume; a normally closed mailbox finishes the process, stop()/scope cancellation end it without a restart, and a fatal drain failure restarts it under restart. The heartbeat comes from Kap.process and beats while the drain runs, including mid-handler.

suspend fun consume(handler: suspend (A) -> Unit)

Runs the drain: every item, in order, through handler — at most one handler at a time. Per-item failures are reported and isolated (MailboxEvent.Failed); an item exceeding itemBudget is cancelled and reported (MailboxEvent.TimedOut); cancellation of the caller is never swallowed. Completes normally when the mailbox is closed and drained.

offer
Link copied to clipboard
suspend fun offer(item: A)

Offers item to the mailbox. Never throws a failure: under the exact strategies it suspends exactly as the strategy prescribes (always for Backpressure.Suspend, only when full for Backpressure.Buffer); under the lossy strategies it never suspends, drops per policy and increments dropped. An offer after close is dropped and counted too, so no caller ever observes a closed-mailbox exception.
